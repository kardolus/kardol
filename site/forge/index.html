The whole house

forge isn't the only machine in the setup. A router decides what every device in the house can see, and a Mac mini builds the apps. Neither forge nor the Mac mini accepts an inbound connection from the internet: web traffic comes back through tunnels forge dials out, and build jobs are work the Mac mini fetches from GitHub.

How sign-in works

Every private app sends you through the same door. Google proves who you are, Keycloak checks that you're on the guest list, and the app checks again.

  1. You open an app

    e.g. photos.kardol.us. With no session, it redirects you to Keycloak with an OIDC request.

  2. Keycloak → Google

    The homelab realm skips its own login page and hands you straight to Google.

  3. Guest-list check

    Back from Google, Keycloak links you only to an account that already exists. Unknown Google accounts are turned away. Nobody can sign themselves up.

  4. Code → tokens

    The app trades the authorization code for tokens server-side, using its own client secret.

  5. App allow-list

    Each app also checks your email against its own list (Grafana admin, the health dashboard and the terminal accept one person).

  6. Session

    A signed cookie keeps you in. SSO sessions last up to 30 days, so one Google sign-in covers every app.

Guests

People outside the house (Nemo app users, someone a Studio page is shared with) sign in through a separate nemo realm. A guest can never become a homelab user.

AI clients

MCP servers (Studio, workbench, Foreman, Nemo) take OAuth tokens from Keycloak, limited by scope and group membership. Claude, ChatGPT and Codex each get their own client.

Machines

The iPhone health exporter posts with a bearer token. Foreman's sandboxed agents get no cluster credentials at all, and the orchestrator holds every key.

Break-glass

Grafana, MinIO and Immich keep a local admin stored in a password manager, so a Keycloak outage can't lock me out.

When something breaks

Two separate paths, because a box that's on fire can't be trusted to report its own fire. The first catches problems while forge is up. The second catches forge itself going dark.

An app or the node misbehaves

forge notices, and tells me
  1. Something is watching

    Blackbox probes load every public URL from inside the cluster. Exporters report on the node, pods, databases, tunnels and backups.

  2. A rule fires

    Prometheus evaluates about 250 alert rules every 30 seconds: site down, ingest stalled, disk filling, backup stale, a certificate about to expire.

  3. Alertmanager sorts it

    It groups related alerts, and a critical alert suppresses the warnings it causes, so one outage is one page and not twenty.

  4. Critical → PagerDuty

    Critical alerts open a PagerDuty incident on my phone. Warnings stay on the dashboard for me to look at later.

  5. Resolved → closed

    When the rule clears, Alertmanager resolves the incident automatically.

forge itself goes dark

silence is the alarm: the dead-man's switch
  1. An alert that always fires

    Prometheus carries a rule called Watchdog that is permanently firing. It means "the alerting pipeline works".

  2. A heartbeat

    Alertmanager sends Watchdog to Healthchecks.io, an outside service, every 5 minutes, and each delivery checks in.

  3. The heartbeat stops

    A power cut, a dead disk, a crashed Prometheus or a home internet outage all look the same from outside: the check-ins stop.

  4. Healthchecks.io pages

    After 10 minutes without a check-in, Healthchecks.io opens a PagerDuty incident itself. Nothing on forge has to be alive for that to happen.

  5. Back up → resolved

    When forge comes back (BIOS powers it on after an outage), the heartbeat resumes and the incident closes.

How the cluster is set up

Deliberately boring: vanilla upstream Kubernetes, one node, no service mesh, no operators the job doesn't need. The cluster can be rebuilt from git. The data is what gets backed up.

Control plane & runtime

  • kubeadm, single node: control plane and workloads share the box (the control-plane taint is removed).
  • A dedicated containerd with its own socket and systemd unit, isolated from Docker on the same host.
  • Scheduler and controller-manager metrics exposed so Prometheus can scrape the control plane.

Networking

  • Flannel CNI (VXLAN) pinned to the wired NIC. Pod CIDR 10.244/16, Services 10.96/12.
  • ingress-nginx as a DaemonSet on hostPort 80. TLS ends at Cloudflare, and the tunnel speaks plain HTTP inside.
  • cloudflared runs as Deployments (and one sidecar). There's no LoadBalancer, and none is needed.
  • Host services (Postgres, MinIO) reach pods through selector-less Services + Endpoints, so apps use normal cluster DNS names.

Storage

  • local-path-provisioner is the default StorageClass, for the few things that need a PVC (Prometheus, caches).
  • Big originals sit on hostPath volumes of type Directory: if the cold drive isn't mounted, the pod won't start, so it never writes to the wrong disk.
  • Databases live outside Kubernetes on purpose: upgrades, dumps and restores stay plain Docker + pg_dump.

Workloads & delivery

  • One namespace per app, each with its own Secrets and a GHCR pull secret. Images are pinned by tag.
  • CronJobs for data work: nightly ingests of NYC open data, pruning that archives before it deletes, Prometheus snapshots to S3.
  • Manifests live in each app's repo. A private infra repo holds the cluster bootstrap, host compose files, secret recreation, and a bare-metal recovery runbook.
  • Agent sandbox: a separate namespace, no service-account token, read-only root filesystem, a non-root UID.

Observability

  • kube-prometheus-stack from a single umbrella Helm chart: 90-day retention, nightly TSDB snapshots into the restic backup.
  • Blackbox probes hit every public URL from inside. 25 Service/PodMonitors scrape the apps, 7 Postgres exporters watch the databases.
  • A dozen hand-built Grafana dashboards, each panel with an explanation. The one below is a trimmed copy of the home board, rendered to an image every five minutes.

Resilience (single-node edition)

  • BIOS powers the box back on after an outage. A static IP and a DHCP reservation keep its address stable.
  • Each night: an etcd snapshot (cluster state, including Secrets) plus PKI and DB dumps into restic, with the critical subset offsite.
  • No HA, by choice. When it's down, it pages me, and recovery is a reboot or a documented rebuild.

Building the apps

Nemo ships to the App Store, the Mac App Store and Google Play from one GitHub Actions workflow. Xcode only runs on macOS, and GitHub charges about ten times more for a macOS minute than for a Linux one: September 2026's releases cost $184 in macOS minutes alone. So the Apple half now runs on the Mac mini at home.

Sharing a desk

The runner lives in its own unprivileged account, in a background login session, at low CPU and disk priority. Whoever sits at the Mac mini keeps a responsive desktop, and the builds never touch their files.

Clean every run

Each job makes a temporary signing keychain and deletes it afterwards, removes its provisioning profiles, and erases the simulator before the tests boot it, the way a fresh cloud machine would hand it over.

If the Mac mini is off

Changing one setting sends every job back to GitHub's own Macs. Slower to start and paid by the minute, but a release never has to wait for the house.
